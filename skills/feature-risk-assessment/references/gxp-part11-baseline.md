# Archive 模块 GxP / 21 CFR Part 11 合规基准线（FMEA 打分用）— v1.1（已确认）

> 用途：作为 FMEA 打分工具的固定参照系。工具读到一条 spec 需求后，先对照这份基准判断"这条需求是达标、超出标准、还是低于标准"，再决定分数和 comment 的措辞。**低于标准的项目，无论其他理由多合理，都不能靠调低分数来"温和处理"，必须在 comment 里明确点名缺什么条款。**

## 0. 适用假设
- 默认这个系统处理的是 GxP 环境下的电子记录（批记录、质量文件、验证文件等），适用 **21 CFR Part 11**（美国）+ **EU Annex 11** + **ALCOA+ 数据完整性原则**中相通的部分；两者在本基准里不做区分，取更严格的一条。
- 如果某个具体 feature 明确只处理非 GxP 的内部行政文档（不属于受监管记录），基准仍适用但整体严重度应该下调——这个判断本身要写进 comment，不能默默下调。

## 1. 访问控制（对应 Part 11 §11.10(d)(g)）
**标准：** 系统必须限制只有经过授权的人员才能使用系统、修改记录、执行操作；权限范围必须能被验证（谁能看什么、谁能改什么是可查的，不是靠约定）。
**打分含义：**
- 权限过滤只在 UI 层做、API 层没有对应校验 → 低于标准，直接影响 d 项（法规不合规），不能只算作"UI bug"。
- 权限模型允许用户看到超出自己授权范围的记录（哪怕是边界场景）→ d 项定为 8-10，且 comment 必须点名"违反 §11.10(d) 访问控制要求"。

## 2. 电子签名（对应 Part 11 Subpart C，§11.50 / §11.70 / §11.100-11.300）
**标准：**
- 签名必须与被签署的记录唯一绑定，不能被复制/转移到其他记录上伪造签署。
- 签名需要记录签署人身份、时间、签署含义（如"确认""批准"）。
- 电子签名需要两个独立的识别要素（如账号+PIN），且要有"未配置签名手段的用户必须先完成配置才能签署"的强制路径。
**打分含义：**
- 签名成功后没有把"签署含义声明"和签署人身份一起落在同一条不可篡改的记录里 → 低于标准，d 项高分。
- PIN 错误时允许无限重试而不锁定/告警 → 属于可以接受的功能缺口，但要在 detectability（g/h）里体现"暴力破解检测缺失"。
- 已有 "e-sign PIN 未设置时引导设置" 这种设计 → 达标，不需要额外扣分。

## 3. 审计追踪（对应 Part 11 §11.10(e)，这是本模块最核心的一条）
**标准：**
- 审计追踪必须是系统自动生成、带时间戳，独立于操作者的操作记录，覆盖"创建/修改/删除"类操作。
- 审计记录本身不能被覆盖或抹除已记录的信息（新增修正记录可以，但不能销毁旧记录）。
- 留存期限不短于对应记录本身的留存期限。
- 必须可供审查/导出（供内部质量部门或监管方核查）。
**打分含义：**
- 只是"应用层不提供编辑/删除入口"，而数据库层面权限本身仍允许 UPDATE/DELETE（应用层拦截，数据库层没拦截）→ 低于标准，因为标准要求的是系统级不可能，不是"没暴露按钮"。**这次 Archive Audit Trail 的 spec 里数据库 service account 只给 INSERT 权限，这是达标甚至优于常见实现的设计，comment 里应该正面点出**。
- 有哈希链防篡改 + 周期性自动巡检 + 主动告警 → 超出 Part 11 字面最低要求（Part 11 只要求"secure, computer-generated audit trail"，没有强制要求密码学链式校验），这是加分项，comment 里应写"超出基准要求的额外保障"，不要因为"公司多做了"就当作理所当然抹平。
- 巡检机制本身如果和被检测的功能是同一套代码、没有独立于该功能之外的第二层校验 → 仍要在 h 项标注为"部分管控"，因为"谁来验证验证机制本身没坏"这一层空白确实存在。

## 4. 数据完整性 ALCOA+ 原则
**标准：** 记录必须做到 Attributable（可追溯到人）、Legible（可读）、Contemporaneous（同步记录不能事后补）、Original（原始或经核实的真实副本）、Accurate（准确）—— 以及扩展的 Complete、Consistent、Enduring（长期可读取，不因格式过时而丢失）、Available（需要时能取出来）。
**打分含义：**
- 归档理由/名称一旦创建不可编辑 → 满足 Contemporaneous + Original，这是设计上主动对齐 ALCOA+ 的表现，可以在 comment 里正面确认。
- 文件格式没有做长期可读性保障（比如只存原始格式，没有考虑格式过时问题）→ 如果 AC/spec 完全没提，属于基准之外未覆盖的风险点，应该在 comment 里指出"当前范围未覆盖 Enduring 原则，建议后续阶段评估"，而不是直接扣分（因为这可能是有意分阶段推进的，不代表当前设计有缺陷）。

## 5. 系统验证与操作检查（对应 Part 11 §11.10(a)(f)(g)(h)）
**标准：** 系统需经过验证（能可靠、一致地产出预期结果，且能识别无效或被篡改的记录）；系统应强制执行合理的操作顺序（不能跳步骤）；应有权限检查和数据来源合法性检查。
**打分含义：**
- 向导强制按步骤走、不能跳过必填项直接提交 → 达标（对应操作顺序检查）。
- **流程性事实（已确认，适用于本阶段所有 feature，不用逐个问）：** FMEA 打分发生在 test strategy 制定之前——测试同事要等风险评估结束后才会介入、才会有 test strategy。也就是说，本阶段被打分的每一个 feature，此刻都必然是"尚未经过正式验证测试（IQ/OQ/PQ）"的状态，这不是某个 feature 特有的缺陷，而是这个阶段所有 feature 的共同起点。
  - 因此：**e 项（likelihood）不能因为"未验证"去逐个额外加分**——因为这对本阶段所有 feature 都成立，不是这个 feature 相对更差；但也**不能反过来用"已验证/测试会覆盖"作为压低 likelihood 或 detectability 的理由**，因为此刻确实没有任何测试执行结果可以引用。
  - comment 里如果要提到验证状态，应该写成中性事实"本阶段尚未进行正式验证测试，本评估结果将作为后续 test strategy 制定的输入"，而不是当作扣分项或加分项去处理。

## 6. 分类与保密（对应数据分类访问控制的一般 GxP 要求，非 Part 11 特定条款）
**标准：** 机密/受限数据的访问必须和其分类匹配，不能因为"这个功能还没做完"就把机密数据当非机密处理。
**打分含义：**
- "Confidential 选项本阶段不可选，所有记录都按非机密处理" → 只要这个阶段确实不存在机密记录（没有数据被错误地放宽保护），这是合理的分阶段设计，不算低于标准；但如果后续阶段允许机密数据先进系统、分类功能却还没跟上，那就是低于标准，必须在 comment 里明确这是"時序风险"（数据先于管控能力进入系统）。

## 打分总原则（写给自己，避免"温和化"）
1. 每一项打分之前，先问：这条需求/设计，达到了上面哪一条基准？达标、超出、还是低于？
2. **低于基准的，必须在 comment 第一句话直接点名缺的是哪条条款**（例如"未满足 §11.10(e) 审计追踪要求"），不能只说"存在改进空间"这种软化措辞。
3. **超出基准的，也要在 comment 里明确写出来**，不要因为分数已经不高就省略——这是给评审人看的证据，说明这不是我漏判，而是设计本身确实做得比最低要求好。
4. 涉及"是否已验证/是否有独立管控"这类基准要求判断，但 spec 里没写的信息，comment 里要明确写"AC/spec 未说明，暂按未达标处理" 或反过来 "已向用户确认，此项从宽处理"——不能含糊带过。
5. **不要把下游 feature 的严重后果重复计入这个 feature 的严重度。** a/b/d 项只打"这个 feature 自己出错，后果是什么"，不要因为它的输出会喂给另一个 feature（比如配置层喂给上传主流程），就把下游那个 feature 已经算过的严重后果（比如"记录永久错误"）再算一遍。那个后果应该留在下游 feature 自己的 FMEA 里体现；这里只需要在 comment 里提一句"该配置错误会传导到 XX feature"，作为背景说明，不作为加分理由。（起因：276931 Archive Manager 真实评分 a/b/d 全部低于我的 dry-run，真实评分把严重度严格限定在"配置层本身"，没有借用 Upload 的不可变后果。）
6. **d 项（法规不合规）打分要认真用上"correctable"这个词本身。** 打分选项原文是"Potential non-compliance, but correctable (4–7)"——如果失效后有审计日志/回滚/管理员纠正等手段能把它变回合规状态，就应该落在 4-7 档，不能只因为这条需求碰了 Part 11 的核心条款就直接跳到 8-10。8-10 留给"一旦发生就没有纠正手段"的场景（比如已上传记录的内容本身错了，改不回来）。审计日志这类东西可以同时体现在 h 项（探测性）和 d 项（可纠正性），这不冲突。
7. **e 项不要拿"spec 写了多少个 scenario"当实现复杂度的替代指标。** spec 写得详细（覆盖很多边界场景）说明需求阶段想得仔细，不代表代码实现起来就一定复杂、容易出 bug——纯 CRUD/权限判断类的逻辑即使 scenario 很多，实现可能仍然简单。没有实际代码/工作量信息时，默认给中低分（3-4），除非 spec 里出现了明确的技术复杂信号（并发、分布式一致性、密码学、状态机嵌套等）。
8. **f 项对"背景信息里的不确定信号"要保持中性，不要往坏的方向解读。** 项目记忆/历史资料里提到的"设计冲突""并行编辑碰撞"等，如果没有被明确定性为"故障/incident"，不要当成"这个功能历史上容易出问题"的证据去加分——很可能只是正常的需求迭代过程。除非有人明确告知这是一次真实故障，f 项默认给新功能的基线分（2-3）。
9. **c 项（患者安全）对纯 metadata/config 类功能，默认给下限（2-3），不要机械套用"间接影响=4"的模板。** 只有当能具体说出"这个配置错了 → 会让某类真实内容/流程受影响"的路径时，才上调到 4 档以上；说不出具体路径的，就该在 1-3 档。
10. **写完分数后自查一遍：这个分数是否和同一格里 comment 描述的档位对得上。** 比如 comment 写"partial controls"却打了一个对应"comprehensive controls"档位的分数，这种自相矛盾要在写入前自己发现，不要留给评审人发现。
